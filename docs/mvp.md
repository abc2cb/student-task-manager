# MVP Student Task Manager

> **Як читати цей документ.** Розділи 1–6 описують MVP практичної роботи №16 — статичну версію в `app/`, де дані зберігалися в пам’яті сторінки. Розділ 7 описує розширену версію самостійної роботи: серверну частину, базу даних SQLite, облікові записи користувачів, пошук, фільтри та сортування (`server/`). Обмеження з розділу 5 стосуються лише версії `app/`.

Документ фіксує межі першої робочої версії продукту (практична робота №16), реалізовані функції, обмеження та фактичні результати перевірки.

## 1. Назва продукту

Student Task Manager — однокористувацький менеджер навчальних завдань студента.

## 2. Мета MVP

Створити однокористувацький менеджер завдань, у якому можна додавати, переглядати, редагувати та видаляти завдання, змінювати їхній стан і фільтрувати список, не втрачаючи вже введених даних під час роботи зі сторінкою.

## 3. Функції поточної версії

| Код | Функція | Як реалізовано |
| --- | --- | --- |
| MVP-01 | Перегляд завдань | Список будується з масиву `state.tasks` функцією `render()`; картка показує назву, дисципліну, термін, пріоритет, опис і стан |
| MVP-02 | Створення завдання | Форма `#task-form`; назва очищується від зайвих пробілів, стан початково «Активне» |
| MVP-03 | Редагування завдання | Кнопка «Редагувати» заповнює ту саму форму; запис оновлюється за `id`, дублікат не створюється |
| MVP-04 | Зміна стану | Кнопка «Позначити виконаним» / «Повернути до активних» перемикає `status` |
| MVP-05 | Видалення завдання | Видалення за `id`; якщо видаляється завдання в режимі редагування, режим завершується |
| MVP-06 | Фільтрація | Кнопки «Усі / Активні / Виконані»; фільтр не змінює основний масив даних |
| MVP-07 | Перевірка назви | Порожня назва та назва лише з пробілів не зберігаються ні під час створення, ні під час редагування |

Додатково, відповідно до попереднього проєкту, реалізовано необов’язкові для MVP поля: дисципліна, термін виконання, пріоритет і опис. Також додано лічильники завдань, позначку «Прострочено» та повідомлення про результат кожної дії.

Модель завдання: `id` (формується програмою, не змінюється під час редагування), `name`, `description`, `category`, `deadline`, `priority` (`low` / `medium` / `high`), `status` (`active` / `done`).

Раніше підготовлені вимоги, user stories та діаграми не видалялися: вони описують повний задум продукту, а цей документ фіксує лише реалізовану частину.

## 7. Розширена версія (самостійна робота)

### 7.1 Що додано порівняно з MVP

Розширена версія працює як клієнт-серверний застосунок: сторінка `server/public/` звертається до REST API, а всі дані зберігаються в базі SQLite. Статична версія `app/` залишена як історія практичної роботи №16 і не використовується.

| Код | Функція | Як реалізовано |
| --- | --- | --- |
| EXT-01 | Реєстрація | `POST /api/auth/register`: ім’я, унікальна адреса, пароль і підтвердження; пароль зберігається як хеш scrypt |
| EXT-02 | Вхід і вихід | `POST /api/auth/login`, `POST /api/auth/logout`; сесія зберігається в таблиці `sessions`, браузер отримує cookie `HttpOnly; SameSite=Lax` |
| EXT-03 | Власні записи | кожен запит до `/api/tasks` фільтрується за `user_id` із сесії; чужі записи недоступні навіть прямими запитами |
| EXT-04 | Збереження даних | таблиці `users`, `sessions`, `categories`, `tasks`; дані залишаються після перезапуску сервера |
| EXT-05 | Пошук | `GET /api/tasks?q=…` — пошук за назвою без урахування регістру |
| EXT-06 | Фільтри | стан, пріоритет і дисципліна; працюють разом із пошуком |
| EXT-07 | Сортування | за терміном (спадання/зростання), пріоритетом (обидва напрями), назвою, датою створення |
| EXT-08 | Стани інтерфейсу | завантаження, порожній список, «нічого не знайдено», повідомлення про помилки полів і помилку сервера |

### 7.2 Структура бази даних

SQL-скрипт створення бази — [`server/db/schema.sql`](../server/db/schema.sql), запуск — `cd server && npm run init-db`.

| Таблиця | Поля | Зв’язки |
| --- | --- | --- |
| `users` | `id`, `name`, `email` (унікальна, без урахування регістру), `password_hash`, `created_at` | — |
| `sessions` | `id`, `user_id`, `created_at`, `expires_at` | `user_id → users.id ON DELETE CASCADE` |
| `categories` | `id`, `name` (унікальна) | — |
| `tasks` | `id`, `user_id`, `category_id`, `title`, `description`, `deadline`, `priority`, `status`, `created_at`, `updated_at` | `user_id → users.id`, `category_id → categories.id ON DELETE SET NULL` |

Обмеження на рівні бази: `title` не може бути порожнім або складатися лише з пробілів (`CHECK (length(trim(title)) > 0)`), `priority` — лише `low/medium/high`, `status` — лише `active/done`. Ідентифікатор запису й власника визначає сервер; поля `user_id` у тілі запиту ігноруються.

### 7.3 Облікові записи та захист даних

- пароль хешується алгоритмом scrypt (N=16384, r=8, p=1) із випадковою сіллю; у базі зберігається рядок `scrypt$N$r$p$salt$hash`, самого пароля немає;
- перевірка пароля виконується через `crypto.timingSafeEqual`, тому час відповіді не залежить від кількості збігів;
- сесія — 64 випадкові байти, зберігається в базі, термін дії 7 днів; cookie недоступна з JavaScript (`HttpOnly`) і не надсилається із сторонніх сайтів (`SameSite=Lax`);
- усі операції читання, редагування, зміни стану та видалення містять умову `user_id = ?`, тому відповідь на чужий запис — `404`, а не `403` (сторонній користувач не дізнається, чи запис існує);
- сервер повторно перевіряє всі поля (назва, дата, пріоритет, дисципліна), тому вимкнення перевірок у браузері не дає змоги зберегти некоректні дані.

### 7.6 Як відтворити перевірки

```bash
cd server
npm install          # зовнішніх залежностей немає, команда нічого не змінює
npm run init-db      # створює data/task-manager.db за схемою db/schema.sql
npm start            # http://127.0.0.1:3000
npm test             # 12 інтеграційних тестів API на тимчасовій базі
```

Для перевірки збереження даних: створити завдання, зупинити сервер (`Ctrl+C`), запустити `npm start` знову й увійти тим самим користувачем — завдання залишиться.

### 7.7 Відомі обмеження розширеної версії

- застосунок призначений для локального запуску; публічного хостингу немає;
- немає відновлення пароля та підтвердження електронної пошти;
